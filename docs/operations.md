# 运行与验收

## 最短验收流程

1. 上传插件 ZIP 并启用，原生配置页应出现当前域名的完整控制台地址。开启开关并保存。
2. 同域登录管理员，进入控制台。普通用户或未登录浏览器不能读取配置、生成邀请或导出诊断。
3. 保存允许赠送的套餐，创建“1 天”测试邀请。确认链接自动带 32 位随机邀请码。
4. 用新邮箱打开链接，在原有注册页完成注册。账号的套餐、权限组、额度、速度／设备限制应匹配所选套餐；到期时间应约为注册后 24 小时。
5. 使用同一链接再次注册，应提示已领取；不会生成第二个账号。尚未领取的邀请撤销后也不能注册。
6. 分别检查 1 个月、1 年、3 年、永久。永久账号到期时间为空，流量不会自动重置。
7. 连接测试机器人、生成绑定指令并私聊发送。用 `/new` 按钮生成邀请，确认网页能看到记录。连续点击同一份草稿的“确认生成”不会创建多份邀请。
8. 在网页关闭控制台。配置操作接口应拒绝访问，TG 仍能操作，已发邀请仍能领取。
9. 开启 Debug，复现遇到的问题后导出诊断 JSON。无需发送 Token、完整邀请链接或账号密码。

## 计划任务与队列

插件通过 XBoard 的插件计划任务接口，每分钟尝试发送通知、重试失败的 Telegram 消息并清理临时交互记录。沿用已有 `schedule:run` 调度及原生队列，不需要额外添加第二套 cron。

在 XBoard 应用目录或对应容器内，可用原生命令检查：

```bash
php artisan schedule:list
```

应能看到 `friend-invite-maintenance`。如果没有，请检查插件启用状态、XBoard 是否支持插件调度，以及常驻进程是否加载了新代码。节点同步由 XBoard 原有队列负责；若账号套餐已正确更新但节点尚未生效，检查原有队列工作进程。

TG 交互收到 Webhook 时会立即尝试发送回复；领取通知通过计划任务发送。失败最多自动尝试 6 次，诊断中的 `pending_messages` 和 `failed_messages` 用于检查。领取通知投递与套餐分配解耦：Telegram 暂时不可用不会撤销已经开通的套餐。

消息属于“至少一次尝试投递”：极端情况下，Telegram 已收下消息但本地未记录成功，重试可能产生重复回复。邀请创建与领取本身另有幂等保护，不会因重复回复重复开通。

## 常见问题

| 现象                             | 检查                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 配置页没有完整地址               | 插件是否已启用；是否仍使用旧的常驻进程；当前分支是否加载插件 ServiceProvider                                      |
| 后台提示管理员权限不足           | 必须同一域名、同一浏览器登录 XBoard 管理后台；不能只登录普通用户页面                                              |
| 后台立即关闭或到期               | 在原生配置页重新开启并保存；检查服务器时间                                                                        |
| 邀请生成失败                     | 检查强制邀请码、全站试用、允许赠送套餐、权限组及额度                                                              |
| 注册页没有自动填邀请码           | 自定义主题可能使用不同参数；修改“注册链接模板”，保留一个 `{code}`                                                 |
| 朋友提示开通失败，随后邮箱已注册 | 可能是原生事务提交后的队列／观察者出错；先登录并核对套餐，勿反复创建账号；查看 `commit_and_native_observers` 事件 |
| 没收到 TG 回复                   | 检查公网 HTTPS、服务器到 Telegram 的网络、是否完成管理员绑定；网页刷新连接状态                                    |
| 机器人有旧 Webhook               | 先在原服务断开，或创建新机器人；插件不会直接覆盖其他地址                                                          |
| 机器人不接受群聊命令             | 本版只接受绑定管理员与机器人的私聊                                                                                |
| 领取成功但无通知                 | 检查计划任务；只有与这份邀请创建管理员相绑定的机器人收到通知                                                      |
| 长链接没有复制按钮               | Telegram 复制按钮最多支持 256 字符；较长链接仍以文本发送，可自行复制                                              |
| 永久套餐额度不重置               | 这是核对版本的 XBoard 原生行为；需要周期重置时请选择有到期时间的期限                                              |

HTTPS 反向代理应正确传递协议和域名；必要时使用 XBoard 自带的 HTTPS 设置。Webhook 必须直接返回正常 HTTP 响应，不能被站点登录页、人机挑战页或缓存替换。

## 数据与停用

插件状态、Token、绑定信息、邀请备注和发送队列内容使用站点 APP_KEY 加密后存入插件表。为了兼容原生注册，原生 `v2_invite_code.code` 仍保存 XBoard 必需的明文邀请码；不能声称整站所有邀请码都是加密存储。

新增表：

- `friend_invite_state`：设置、后台期限、机器人和交互草稿。
- `friend_invite_invitations`：邀请记录、原生邀请码关联及核销结果。
- `friend_invite_updates`：机器人更新去重。
- `friend_invite_outbox`：加密的待发送消息及重试状态。
- `friend_invite_events`：脱敏诊断事件。

常规备份同时保留数据库和 APP_KEY。更换 APP_KEY 前需处理这些加密数据，不能直接丢弃旧密钥。

关闭控制台只禁止网页操作；已下载的信息不可能被远程收回。暂停好友注册会阻止新建及领取邀请。禁用插件会撤销待领取邀请，恢复 XBoard 原生注册行为；如果要同时关闭全站注册，请另外使用 XBoard 的注册开关。

卸载默认保留插件表和已经开通的账号，重新安装可以读取原有数据；禁用时被撤销的邀请不会恢复。无需保留数据时应先备份，再单独安排清理，插件不自动删除用户账号。

## 与其他插件共存

本插件没有改动订阅桥接。开通后账号获得 XBoard 权限组，订阅桥接自然按这个权限组决定外部节点是否可见。两者分别维护邀请和外部订阅，均遵循原有管理员鉴权。

若其他插件也替换 RegisterService、改变注册钩子返回行为或自动分配试用套餐，需要单独验证组合。XBoard 原生 `user.register.after` 钩子仍在原生注册服务内部执行，其执行时点早于本插件最后分配赠送套餐；不要把那个钩子当作“赠送套餐已经提交”的通知。
